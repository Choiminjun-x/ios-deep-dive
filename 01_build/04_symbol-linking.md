# 심볼과 링킹

> 작성일: 2026-10-08

## 1. 심볼

- 함수나 전역 변수에 붙은 이름표 → 나중에 실제 주소로 바뀔 자리
- 컴파일러는 파일을 하나씩 기계어로 바꾼다 → 실제로 최종 실행 파일의 몇 번지에 놓일지 아직 모른다

```
main.o의 기계어:  "jump → [greet 주소 ??]"
                          ↑
                   이 이름표가 심볼
```

### nm으로 심볼 보기: U, T

- `nm`이 붙이는 표시
- `.o` 안의 이름표는 눈에 안 보인다. `nm`은 그 이름표 목록을 꺼내 보여 주는 도구이고, 이름표마다 상태를 한 글자로 붙여 준다
  - U: 필요하다는 쪽
  - T: 실물(정의)이 들어 있는 쪽

## 2. 링킹

- 따로 컴파일된 `.o` 조각들을 하나로 이어 붙이고, 이름표를 실제 주소로 바꾸는 것
- 이걸 하는 도구가 링커(`ld`)

```
main.o    [jump → greet??]
Greeter.o [greet: "hi"]
      │
      ▼  ld
① 이어 붙이기 → greet이 0x1000번지에 놓임
② "greet??"를 찾아서 → 0x1000으로 채움

실행 파일  [jump → 0x1000] ... [0x1000: greet "hi"]
```

### 왜 굳이 나눠서 컴파일할까?

- 빠르다: 파일 하나 고치면 그 파일만 다시 컴파일하고 링크만 다시 한다 (증분 빌드)
- 남의 코드는 이미 컴파일된 상태로 온다: UIKit이나 상용 SDK는 소스가 없다. 내 코드와 이어 붙일 방법이 링킹뿐이다

### 링킹이 잘됐는지 보려면?

```
링크 전 (.o)         U/T가 섞여 있음 → 누가 필요하고 누가 가졌나
      ↓ ld
링크 후 (실행 파일)   U가 거의 사라짐 → 남은 U는 동적 라이브러리 몫뿐
      ↓ 실행
dyld                남은 U를 그 라이브러리에서 찾아 채움
```

링크가 끝난 실행 파일에서도 U가 일부 남는 게 정상이다. UIKit, libswiftCore 같은 동적 라이브러리의 함수는 실행 시점에 dyld가 채우기 때문이다.

### 링크 에러: Undefined symbol, duplicate symbol

링커의 규칙은 하나다. 이름표(U) 하나당 실물(T)은 정확히 1개.

```
T가 0개   → Undefined symbol   (채울 실물이 없음)
T가 1개   → ✅
T가 2개+  → duplicate symbol   (어느 쪽으로 채울지 못 고름)
```

같은 실수라도 Swift는 컴파일 단계에서 먼저 잡는다. 컴파일러가 아는 범위가 다르기 때문이다.

| | 컴파일러가 아는 것 | 정의가 없으면 | 정의가 둘이면 |
|---|---|---|---|
| C / ObjC | 이 파일 + 헤더의 선언 | 링크 ❌ `Undefined symbol` | 링크 ❌ `duplicate symbol` |
| Swift (같은 모듈) | 모듈 전체 파일 | 컴파일 ❌ `cannot find '…' in scope` | 컴파일 ❌ `invalid redeclaration` |

- C는 헤더에 선언만 있으면 컴파일을 통과시키고 U를 남긴다. 정의를 찾는 건 링커 몫이다
- Swift도 모듈 경계를 넘으면 링크 에러가 난다. 예: `import`는 되는데(`.swiftmodule`이 보임) 바이너리가 링크 대상에 없을 때, bridging header의 ObjC 헤더는 있는데 `.m`이 타겟에서 빠졌을 때
- 에러 메시지의 `referenced from:`은 U를 가진 쪽(필요한 쪽)이다. T를 가져야 할 쪽은 `nm`으로 직접 확인한다

## 3. 정적 라이브러리와 동적 라이브러리

### 형태별 구분

- `.a`: 항상 정적
- `.dylib`: 항상 동적
- `.framework`: 둘 다 가능 → 바이너리 확인 필요
- `.xcframework`: 안에 든 것에 따라 다름 → 슬라이스 안을 확인

### 비용을 내는 시점

- 정적: 비용을 빌드 때 낸다 → 링커가 미리 다 합쳐 둠, 실행 때 할 일이 적음
- 동적: 비용을 실행 때 낸다 → 메모만 남겨 둠, 켤 때마다 dyld가 찾아서 연결

### Pre-main: 동적 프레임워크 하나당 dyld가 하는 일

```
앱 아이콘 탭
 → 커널: MyApp 매핑
 → dyld: 의존 목록(otool -L) 읽기
     프레임워크마다 반복 ──────────────────────┐
       ① @rpath에서 파일 찾기, 열기, 매핑        │
       ② 코드 서명 확인                          │ × 앱이 들고 온
       ③ 이름표 → 주소 채우기 (bind)              │   동적 프레임워크 수
       ④ 초기화 코드 실행 (+load, static init)    │
     ─────────────────────────────────────────┘
 → main()
```

- UIKit 같은 OS 프레임워크는 dyld shared cache에 미리 합쳐져 있어 비용이 거의 없다 → 문제는 `@rpath/` 개수
- iOS 13 이후 dyld가 이 작업의 상당 부분을 미리 계산해 캐시(launch closure)해 두기 때문에 예전만큼 극적이진 않지만, 개수에 비례하는 비용은 여전히 남는다

### 앱 크기

- 정적: 쓰는 코드만 들어가고, 안 쓰는 함수는 지운다. 단, 타겟마다 복사 → 커짐
- 동적: 공개 함수는 전부 남는다. 링커는 앱이 뭘 쓸지 모르니 다 남겨 둬야 한다. 한 벌로 여러 타겟이 공유할 수 있다

## 셀프 체크

**Q1. 동적 프레임워크는 왜 "안 쓰는 함수 지우기"를 못 하나?**

- 동적 프레임워크의 함수는 실행 시점에 dyld가 앱의 U를 프레임워크의 T 주소로 채우는 방식으로 연결된다. 그래서 프레임워크를 링크하는 시점에는 어떤 앱이 어떤 함수를 쓸지 알 수 없다. 따라서 공개 함수는 안 쓰여도 전부 남겨야 하고, Dead Code Stripping으로 지울 수 있는 건 공개 함수에서 닿지 않는 내부 함수뿐이다.
